# プロジェクト振り返り報告書

## 読み手

既定の読み手は**技術が分かる経営者**とする。プロジェクトによって読み手が違う場合は、この節を書き換えてから使うこと（読み手が変われば、何を書くべきかが変わる）。

技術が分かる経営者に向けて書く場合の指針は以下のとおり。

- アプリ側の用語（画面・API・データの扱い・言語やフレームワーク）はそのまま使ってよい
- **インフラ側（ホスティング・実行環境・DB の権限設定・通信プロトコル）は用語のまま置かない。** 「サーバーレスはインスタンスごとにメモリが独立する」のように前提知識を要する話は、**利用者から見て何が起きるか**に書き換える。書き換えられないなら、その項目自体が読み手の判断材料になっていない
- **HTTP ステータスコード（`429` など）は使わない。** 画面に出る文言（「試行回数が多すぎます」）や、利用者から見た結果で書く
- ただし技術の説明で終わらせない。**その技術判断が何を意味するか**（利用者への影響・リスク・コスト・今後の選択肢）に必ず接続する
- 読み手が知りたいのは「何を作ったか」ではなく「**何が良くなり、何が残っていて、次に何を決める必要があるか**」
- 実装の詳細を列挙しない。判断の分かれ目と、その結果に絞る

## 0. README.md の同期を確認する

README.md は §2 の情報源であり、実体とずれていると誤りをそのまま報告書に引き継ぐ。**事実収集の前に**、同期が必要かを次の2つで判定する。

```powershell
# (1) README.md の最終更新以降に、構成に関わるパスが変わったコミットがあるか
$base = git log -1 --format=%H -- README.md
git log --oneline "$base..HEAD" -- .claude/commands .claude/agents .claude/skills .claude/project.json stacks

# (2) 未コミットの構成変更があるか
git status --short -- .claude/commands .claude/agents .claude/skills .claude/project.json stacks README.md
```

**どちらかに出力があれば `readme-syncer` エージェントを実行してから §1 へ進む。** 両方とも空なら同期は省略してよい（構成が変わっていないのにエージェントを走らせても、README は変わらない）。

制約が2つある。いずれも判定を過信しないための注意点であり、**迷ったら実行する側に倒す**。

- **呼び出し元がメイン会話のときだけ実行できる。** `retrospective-writer` は Agent ツールを持たず自分で呼べないため、委任前に呼び出し元が済ませる
- **ディレクトリ構成の変更は取りこぼす。** git はディレクトリ単体を追跡せず、`.gitignore` 対象の新設ディレクトリ（`logs/` など）は (1)(2) のどちらにも現れない。README のツリー図に関わる変更に心当たりがあれば、判定結果によらず実行する

## 1. 対象範囲を確定する

**既定はプロジェクト全体**（最初のコミットから HEAD まで）。引数（`$ARGUMENTS`）で範囲が指定された場合のみ、それに絞る（例: `PR#13` / `直近1週間` / `feature/xxx ブランチ`）。

範囲を確認するためにユーザーへ問い返さない。指定が無ければ全体として進める。

## 2. 事実を収集する

**コミット本文（`%b`）まで読む。** 判断理由・背景・実測値は本文に書かれていることが多く、ここが「工夫した点」「学んだこと」の主要な情報源になる。件名（`%s`）だけでは判断の背景が落ちる。

ただし**git はあくまで情報源であり、報告書にはコミットハッシュもリンクも書かない**（[template.md](template.md) の「書き方の指針」）。裏取りに使い、結論だけを書く。

```powershell
git log --reverse --format="%ad %h %s" --date=short   # 全体像
git log -1 --format="%s%n%b" <hash>                    # 個別の意図
git show <hash> -- <path>                              # 実際の差分
```

補助ソース:

- `README.md` / `docs/` — 現在の機能・構成・運用ルール。同期は §0 で確認済みの前提。それでも記述を鵜呑みにせず、報告書に載せる事実は実体で裏を取る
- Claude Code のメモリ（このプロジェクト用のメモリディレクトリ）— 運用方針・過去の実測記録
- 削除されたドキュメント — 運用上削除したファイルの内容は git 履歴にのみ残る: `git show <削除コミット>^:<パス>`

**「未確認」で終える前に、確認手段を作れないか検討する。** リポジトリに答えが無くても、確認用のクエリやスクリプトのように、その場で用意できる確認手段があることがある。作れる場合は用意してユーザーに提示し、確認が済んだら破棄する（確認用の使い捨てファイルは成果物に残さない）。

## 3. 執筆する

[template.md](template.md) の骨子・各見出しの書き分け・**分量の上限**に従う。

網羅より簡潔さを優先する。集めた事実を全部載せない。読み手の判断に効かない事実は、確認できていても書かない。

## 4. 提出前に自己検査する

書き出す前に、[template.md](template.md) の判定テストと分量の上限を守れたかを確かめる。**ルールを書くだけでは守れない**（上限を決めた本人が、同じセッションの中で超えることがある）。

- **見出しごとに項目数を数える。** 小見出しで分けた場合はその単位で数え、「判断を仰ぎたい」項目は数に入れない。上限は6項目
- **合否判定を全項目に当てる。** 工夫した点・改善したい点・学んだことには [template.md](template.md) にそれぞれ判定テストがある。まとめて眺めず、1項目ずつ通す
- **コミットハッシュが本文に残っていないか検索する**（7桁以上の16進数を探す）
- **HTTP ステータスコード・インフラ側の用語が残っていないか確認する**（「読み手」の節を参照）。3桁の数字を機械的に探すと件数に引っかかるため、**サーバーの応答を指して使われている数字か**で判定する
- **「判断を仰ぎたい」項目に、現状・影響・決めるべきことの3つが揃っているか確認する。** 圧縮の過程で影響と判断が同時に落ち、見出しだけが残ることがある

## 5. 書き出す

出力先は `docs/retrospective-<YYYY-MM-DD>.md`。日付は `Get-Date -Format "yyyy-MM-dd"` で取得する。同名ファイルが既にある場合は**上書きせず**、内容を確認したうえで追記か別名かをユーザーに確認する。

## 6. 追跡対象外を確認する

```powershell
git check-ignore -v docs/retrospective-<YYYY-MM-DD>.md
```

出力が無ければ `.gitignore` に `docs/retrospective-*.md` を追加する。

## 7. コミットしない

作業ツリーに残して報告する（[git-rules.md](../../../docs/git-rules.md)）。

## 禁止事項

- **推測で書くことを禁止する。** 「たぶんこうだったはず」「おそらく〜のため」は一切書かない。一次資料（git 履歴・実ファイル）で確認できた事実だけを書く。確認できないことは、**書かない**か「未確認」と明記するかの二択とし、確認できた事実であるかのように混ぜない（[factcheck.md](../../factcheck.md)）
- **推測に基づく因果・意図の断定を禁止する。** コミット本文に理由が書かれていない変更について、「〜のために変更したと考えられる」と動機を創作しない
- 実在しないコミット・PR・指摘・レビュー・数値を作らない
- 数値・日付・固有名詞を裏取りせずに書かない。コミット件数は `git log --oneline | Measure-Object -Line`、データ件数はコミット本文やドキュメントの実測値を根拠にする
- 「改善したい点」に、未対応であることを確認していない事項を書かない（コードやドキュメントで実際に確認する）

## 注意事項

- 出力先は `.gitignore` 対象のため /check のドキュメント検査（`verify-docs.ps1`）が掛からない。ドキュメント内リンクは自分で確認する
- 範囲が広く git 履歴でコンテキストを圧迫する場合、調査は `Explore` エージェントに委任してよい
