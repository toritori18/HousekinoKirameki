# 振り返り報告書の出力テンプレート

読み手は**技術が分かる経営者**。技術用語はそのまま使ってよいが、技術の説明で終わらせず、必ず「それが何を意味するか」まで書く。

## 骨子

見出しは以下の4つで固定（順序も変えない）。

```markdown
# ふりかえり（<対象範囲>・<開始日>〜<終了日>）

<アプリ概要：1行>

<冒頭サマリ：3〜4行>

## 成果
## 工夫した点
## 改善したい点
## 学んだこと
```

### アプリ概要（1行）

**最初の1行は、何のアプリかの説明にする。** ふりかえりの内容ではなく、読み手が対象サービスを思い出すための1文。空行で冒頭サマリと分ける。

- 「何を扱い、誰が、何をできるか」を1文で書く（例: `社内の申請書類を検索し、承認の進み具合を追える Web アプリ`）
- **現状に合わせる。** 停止中の機能を「できる」と書かない（新規登録を止めているなら「招待されたユーザーが」と書く）
- 技術スタックはここに書かない（「成果」で扱う）

### 冒頭サマリ（3〜4行）

ここだけで判断できるよう、以下を含める。アプリ概要と重複する数値は片方だけに書く。

- 対象範囲・期間・規模（コミット数など、根拠のある数値）
- **この期間で何が前に進んだか**を1文
- **判断・対応が必要な残件があるか**を1文（無ければ「無し」と明記）
- このファイルを版管理しない旨

## 各見出しの書き分け

| 見出し | 書く内容 | 避けること |
|---|---|---|
| 成果 | 利用者・サービスから見て**何ができるようになったか**。機能／データ基盤／開発基盤などの単位でまとめ、技術要素は「何を可能にしたか」に接続する | 着手しただけのものを成果に含める。実装作業の列挙で終える |
| 工夫した点 | 判断が分かれた場面での選択と根拠。**何を取り、何を捨てたか（トレードオフ）**をセットで書く | 単なる作業手順の列挙。選択肢が1つしかなかったものを工夫として書く |
| 改善したい点 | 未対応・積み残し・根拠が弱いまま暫定値の箇所。**放置した場合に何が起きるか（影響）**と、判断を仰ぐ必要があるものを明示する | 反省の言葉で終える。影響の見積もりなしに列挙だけする |
| 学んだこと | **次に同じ場面が来たときに役立つこと**、および**再発防止に効く知見**。外部サービスの暗黙仕様やハマりどころは**再現条件**まで書く | 一般論・教科書的な記述。プロジェクト固有でない話。起きたバグの経緯報告（何が壊れていたかを書くだけで、次の判断が変わらないもの） |

**「工夫した点」の合否判定。** 各項目に「他に現実的な選択肢はあったか」を当てる。選択肢が無かったもの＝**定石どおりの実装は、正しく実装できていても工夫ではない**（認可を fail-closed にする・サーバー側で認可を検証する・CI で lint・型検査を回す、はいずれも落ちる）。ただし**捨てずに移す**——定石の実装に埋まっている未決の選択は「改善したい点」へ、実測値は根拠として本文へ回す。

**「改善したい点」の合否判定。** 各項目に「放置すると実際に何が起きるか」を当て、**実測で答えられないものは載せない**。一般的な開発基盤が無いという指摘（自動テスト・フォーマッタ・監視の未導入）は、「無い」と書けば必ず正しく見えるため混入しやすい。書く前に実害を測る——「フォーマッタ未導入」と書く前に、書式が実際にどれだけ揺れているかを数える。数えた結果、揺れているのが一部の項目だけなら、それは改善したい点ではない。

**「学んだこと」の合否判定。** 各項目に「次に同じ場面が来たとき、これを読んで何を変えられるか」を当てる。答えが出ないものは、事実として正しくても載せない——削除するか、未決の判断が残っているなら「改善したい点」へ移す。同じ教訓に収束する項目が複数あるときは、再現条件が最も具体的な1つに寄せる。

## 分量

**短く書く。長さは価値ではない。** 読み手は経営者であり、読む時間が最も高価な資源である。

- **各項目は原則2文、長くても3文。** 「なぜ／どうなったか」まで書く必要はあるが、それは1文足せば済む。4文以上になったら、削れる前置きが混ざっている
- **同じ事実を複数の見出しに書かない。** 1つの事実は最も効く見出しで1回だけ扱う（例: 外部サービスの取得件数の上限は、成果か学んだことのどちらか一方。両方で説明しない）
- **経緯の前置きを削る。** 「〜だったため〜した」は「〜した」で足りることが多い。背景が判断の理解に不可欠なときだけ残す
- **6項目まで。** 小見出しで分けた場合はその単位で数える。超えるなら、粒度が細かすぎるか、実装作業を列挙している

例外: **「判断を仰ぎたい」項目は圧縮せず、項目数にも数えない。** 判断に必要な材料（現状・影響・何を決める必要があるか）が落ちると、項目自体が役に立たなくなる。読み手が最も必要とする部分であり、ここを削って全体を短くするのは本末転倒。

## 書き方の指針

- **結論を先に書く。** 各項目は「何が起きたか／どうなったか」から始め、経緯は必要な範囲で後述する
- **コミット情報は本文に一切書かない。** ハッシュ・コミットリンク・「〜のコミットで対応」といった言及を含む。読み手は経営者であり、どのコミットで直したかは判断材料にならず、文を長くするだけ。**裏取りには必ず使うが、成果物には出さない**
- 参照してよいのは、読み手が意味を追える単位だけ（`PR #4〜#10`、日付、ファイル名・スクリプト名）
- 数値を出すときは根拠（実測日など）を添える。根拠を示せない数値は書かない
- 断定できない事柄は「未確認」と明記する。推測を事実のように書かない
